# Agent Skill 分析画像

Skill 可以是单一目录、技能集合，或宿主项目内的一种扩展。命中后以 `skills/` 为主归属根；若同时是 Extension，manifest 或等价计划指定主归属，另一域只引用接缝。首先确定分析单元和宿主契约，再分析具体 Skill。`artifacts` 模式由 `skills/README.md` 负责集合目录、形态分簇、宿主关系和单项分析链接；`inline` 模式给出等价章节。

## 集合级分析

对包含多个 Skill 的仓库：

1. 盘点每个 Skill 的 name、description、调用策略、资源和外部依赖；
2. 根据问题域和实现形态分簇，识别共享参考、脚本、重复流程和路由冲突；
3. `survey` 建立目录或等价清单并选择代表性样本；`standard` 覆盖所有 Skill 的契约并深入关键样本；`deep` 覆盖 manifest 或等价计划纳入范围的全部 Skill；
4. 样本选择记录理由，不把样本结论扩展到未读取的 Skill。

## 单个 Skill 必答主题

### 意图与路由

- Skill 解决什么特定问题，为什么值得独立存在？
- name/description 是否覆盖真实调用方式，是用户调用还是模型调用？
- 哪些相邻请求应路由到其他 Skill 或普通能力？
- 运行时、工具、权限、仓库状态和用户输入的前置条件是什么？

### 信息层级

- 哪些内容常驻在元数据、主指令和按需参考中？
- 参考文件的指针是否说明了读取条件和分支？
- 每个含分支的流程是否只加载相关资源？
- 是否存在重复真实来源、失效缓存或无调用路径的孤立文件？

### SOP 与完成标准

- 执行阶段的输入、行为、产物和状态转移是什么？
- 每一步是否有可检查且足够完整的完成标准？
- 哪些细节通过确定性脚本完成，哪些需要 Agent 判断？
- 用户授权、外部副作用和停止条件位于何处？

### 脚本、工具与资源

- 脚本的参数、输出、stderr、退出码、幂等性和外部依赖是什么？
- 脚本是否将重复的确定性工作从自然语言指令中抽离？
- references 是行为指令还是领域事实；assets 是否确实属于生成结果？
- 资源路径、运行时和宿主工具的假设是否成立？

### 安全与评测

- 外部文件和工具输出是数据还是可执行指令？
- 文件系统、网络、凭据、破坏性操作和外部消息的权限边界是什么？
- 失败、部分完成、重试、`unknown`、`not-applicable` 和人工介入如何表达？
- 是否有真实请求、可观测产物和行为不变条件的前向测试？已有测试作为证据读取，不因分析而执行。

## 形态标签

形态可多选，不将其当作互斥等级：

- `instruction-driven`：主要价值来自 SOP、判定标准或领域参考；
- `script-backed`：确定性任务由脚本或工具执行；
- `router`：根据用户意图或环境证据加载不同分支；
- `artifact-centric`：执行过程产生持久化中间产物或最终文件；
- `delegating`：通过子 Agent 或多阶段任务分治。

## 完成标准

- Skill 的调用分支、不适用边界和前置条件已映射；
- 主指令的每个执行阶段均有可检查的终止条件；
- 每个被引用的资源都有读取条件和真实调用路径；
- 所有脚本的 I/O、副作用、失败语义和依赖已说明，关键行为有可重复验证或明确未验证；
- 评价区分已验证事实、文档声明、设计推断、未知项和改进建议。
