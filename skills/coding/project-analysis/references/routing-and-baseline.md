# 路由与公共基线

本文件定义仓库层级、画像选择、分析目标、深度和公共问题。能力画像只在触发证据存在时加载；没有适用画像时仍可完成公共基线，并在 `artifacts` 模式的 manifest 或 `inline` 模式的等价计划中记录未命中原因。

## 分析对象

按以下层级建模，不要将整个仓库强制归为一种项目：

```text
Repository
└── System（可运行系统）
    └── Package / Module
        └── Capability
            └── Flow / Mechanism
```

Monorepo 先识别可独立构建、运行或发布的 System，再分析它们之间的契约。目标是子目录时，仍记录其所属 Git 仓库和相对路径。

能力画像决定分析产物的知识所有权，不替代上述仓库层级：一个 System 可同时贡献多个能力域，同一画像也可横跨多个 System。画像之间允许多标签命中，但同一事实必须有一个主归属域；跨域交接写入 `flows/`，横切治理写入 `quality/`。

## 公共基线

所有适用的问题都要回答；不适用的问题写为 `not-applicable`，无法从仓库现有材料确认的问题写为 `unknown`。公共基线默认使用静态证据，不主动运行代码。

### 定位与边界

- 项目为谁解决什么问题？
- 核心使用场景和主路径是什么？
- 系统自身负责什么，哪些责任属于上下游？

### 仓库与运行

- 有哪些 System、Package/Module，它们的职责和依赖方向是什么？
- 构建、启动、测试、发布和部署入口在哪里定义？
- 配置、环境变量、特性开关和运行时依赖位于何处？

### 架构与主链路

- 外部输入通过哪些入口进入？
- 一条代表性请求或任务如何到达终态？
- 模块通过什么接口或协议协作？哪些接缝存在两种以上实现？
- 数据、控制和事件分别如何流动？

### 领域、状态与持久化

- 核心名词、实体、值对象和不变条件是什么？
- 哪些对象拥有生命周期，状态转移的触发、守卫和副作用是什么？
- 数据如何存储、索引、缓存、迁移和清理？没有持久化时说明边界。

### 质量与运营

- 单元、集成、端到端和回归测试分别覆盖什么？
- 代码如何表达超时、重试、取消、并发、背压、部分失败和资源释放？
- 身份、授权、秘密、信任边界和高危操作如何治理？
- 日志、指标、追踪、审计和故障诊断如何建立？

### 取舍与风险

- 代码中哪些选择表明作者优先保护什么？
- 获得了什么，牺牲了什么？
- 已验证风险、推断风险、未知项和未执行验证分别是什么？

## 分析目标

| Goal | 加强的分析角度 |
|---|---|
| `onboarding` | 构建运行入口、导航图、主链路和建议阅读顺序 |
| `architecture` | 模块接口、依赖方向、状态、协议和设计取舍 |
| `learning` | 代表性机制、设计意图、可迁移经验和实现限制 |
| `reimplementation` | 类型、协议、状态机、算法分支、外部桩和覆盖范围；输出蓝图，不执行实现 |
| `reproduction` | 基于仓库代码、配置、日志和文档整理训练/实验执行流程与最终参数；输出供人执行的说明，不安装、下载或运行 |
| `security` | 资产、信任边界、权限传递、输入验证、敏感信息和审计 |
| `performance` | 关键路径、I/O、并发、缓存、批处理、资源上限和已有测量证据 |
| `extension-development` | 扩展点、宿主契约、生命周期、兼容性、打包与调试 |

## 深度

- `survey`：建立仓库地图，追踪一条主链路，将适用主题压缩到总览。
- `standard`：追踪主链路与主要边界路径，对重要能力生成分册。
- `deep`：覆盖所有有实质证据的重要能力、关键变体与边界路径，并按 goal 生成专门机制分析。

深度控制证据覆盖和机制粒度，不通过指定文档数量凑满配额。`reproduction` 是分析目标，不等同于必须执行训练或评估。
