# 路由与公共基线

## 分析对象

按以下层级建模，不要将整个仓库强制归为一种项目：

```text
Repository
└── System（可运行系统）
    └── Package / Module
        └── Capability
            └── Flow / Mechanism
```

Monorepo 先识别可独立构建、运行或发布的 System，再分析它们之间的契约。

能力画像决定分析产物的知识所有权，不替代上述仓库层级：一个 System 可同时贡献多个能力域，同一画像也可横跨多个 System。只有具有独立内部机制的画像获得能力域目录；跨画像接缝归 Flow，横切治理归 Quality。

## 公共基线

所有项目均回答以下问题；`survey` 可合并到总览，`standard/deep` 根据复杂度拆分。

### 定位与边界

- 项目为谁解决什么问题？
- 核心使用场景和主路径是什么？
- 系统自身负责什么，哪些责任属于上下游？

### 仓库与运行

- 有哪些 System、Package/Module，它们的职责和依赖方向是什么？
- 如何构建、启动、测试、发布和部署？
- 配置、环境变量、特性开关和运行时依赖位于何处？

### 架构与主链路

- 外部输入通过哪些入口进入？
- 一条代表性请求或任务如何到达终态？
- 模块通过什么接口或协议协作？哪些接缝存在两种以上实现？
- 数据、控制和事件分别如何流动？

### 领域、状态与持久化

- 核心名词、实体、值对象和不变条件是什么？
- 哪些对象拥有生命周期，状态转移的触发、守卫和副作用是什么？
- 数据如何存储、索引、缓存、迁移和清理？

### 质量与运营

- 单元、集成、端到端和回归测试分别覆盖什么？
- 如何处理超时、重试、取消、并发、背压、部分失败和资源释放？
- 身份、授权、秘密、信任边界和高危操作如何治理？
- 日志、指标、追踪、审计和故障诊断如何建立？

### 取舍与风险

- 代码中哪些选择表明作者优先保护什么？
- 获得了什么，牺牲了什么？
- 已验证风险、推断风险和待验证问题分别是什么？

## 分析目标

| Goal | 加强的分析角度 |
|---|---|
| `onboarding` | 构建运行、导航图、入口、主链路和建议阅读顺序 |
| `architecture` | 模块接口、依赖方向、状态、协议和设计取舍 |
| `learning` | 代表性机制、设计意图、可迁移经验和实现限制 |
| `reimplementation` | 类型、协议、状态机、算法分支、外部桩和覆盖范围 |
| `reproduction` | 原始实现快照、数据与环境、最终训练参数、执行命令、指标和复现缺口 |
| `security` | 资产、信任边界、权限传递、输入验证、敏感信息和审计 |
| `performance` | 关键路径、I/O、并发、缓存、批处理、资源上限和测量证据 |
| `extension-development` | 扩展点、宿主契约、生命周期、兼容性、打包与调试 |

## 深度

- `survey`：建立仓库地图，追踪一条主链路，将各主题压缩到总览。
- `standard`：追踪主链路与主要失败路径，对重要能力生成分册。
- `deep`：覆盖所有有实质证据的重要能力、关键变体与边界路径，并按 goal 生成专门机制分析。

深度控制证据覆盖和机制粒度，不通过指定文档数量来凑满配额。
