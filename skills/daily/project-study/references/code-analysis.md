# Code Analysis — 源码解释的证据规则

在用户问**具体函数、模块、调用链、设计取舍**，或学习流程需要深入一个纵向切片时读取。此文档只负责代码研究的可核验性；单元进度、完成状态由 [学习流程](learning-workflow.md) 决定。

## 研究步骤与局部完成条件

1. **圈定行为**：确定本次解释的输入、输出及最相关的 route、CLI、事件处理器、任务或公开 API。完成：一个明确入口及其可定位符号。
2. **追踪主链**：沿调用者 → 被调用者查看关键函数，记录参数、返回值和外部副作用。完成：从入口到一个明确结果点，必要节点均有文件/符号对应。
3. **解释数据与状态**：说明关键对象何时创建、转换、缓存、持久化或释放；如涉及异步、事务或模型状态，指出生效边界。完成：能说明至少一次重要的数据或控制流转换。
4. **检查反例**：沿一个相关条件分支、异常或失败路径验证边界。完成：指出一处有源码依据的行为限制或明确说明未覆盖。
5. **讨论设计**：先解释当前代码实际行为，再讨论它的收益、代价和可替代方案。完成：已核验的实现与推测的设计动机分别标注。
6. **给出验证机会**：优先定位测试或设计静态推演题；需要实际运行时遵守主 Skill 的授权边界。完成：学习者拥有一个可以检查自己判断的动作。

## 证据等级

| 等级 | 记录方式 |
| --- | --- |
| 源码确认 | 当前工作树的相对文件路径、符号，已核实才附具体行号 |
| 文档描述 | 标明来自 README/文档，尚需对应到实现 |
| 静态推导 | 说明由哪些语句或分支推导，以及尚未覆盖的动态条件 |
| 动态观察 | 只有真正执行后才写运行命令、环境和实际输出 |
| 设计假设 | 使用“可能原因”“一个替代方案”，不将推测写成作者动机 |

源码的基线记录使用主 Skill 约定。遇到反射、注册器、宏、依赖注入、框架生成代码等动态连接时，确认实际绑定点；找不到则标记“待核实”。文档与源码冲突时，说明两者的差异及当前结论的证据范围。

## 交付格式（按问题规模裁剪）

**核心结论 → 有证据的代码路径 → 数据/状态变化 → 边界与设计取舍 → 可验证的问题或实验。**

一次简单技术问答只需够回答该问题的范围；复杂链路才使用完整结构。路径和符号无法核实时明确说明缺口。若当前有学习单元，在解释后给出原单元的下一动作。

**完成门槛**：关键结论均有相应证据等级，主路径和未知连接分得清楚，学习者知道如何核验；不能把未执行的测试描述为通过。
