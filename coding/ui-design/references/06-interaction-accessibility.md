# 06 · 交互与无障碍：让界面能被使用而非仅能被观看

## 主流程状态表

对关键动作写 `触发 → 等待 → 成功 / 失败 → 恢复`。不是每个按钮都要有八种外观，但每个**真实存在**的关键状态都应有明确行为：

| 状态 | 用户能观察到什么 | 工程注意 |
| --- | --- | --- |
| default | 控件用途和可点击范围清晰 | 使用正确语义元素 |
| hover | 可选的指针反馈 | 触屏不可依赖 hover |
| focus | 清晰可见的键盘焦点 | 不全局删除 focus outline |
| loading | 操作进行中，避免不明重复提交 | 合理锁定重复提交，不丢输入 |
| success | 明确的结果或后续位置 | 不只是瞬间变绿 |
| empty | 为什么空、下一步做什么 | 区分初始空和无搜索结果 |
| error | 哪儿失败、怎么修复或重试 | 不泄漏隐私或原始堆栈 |
| disabled | 不可操作原因在适当位置可见 | 不仅通过灰色传达含义 |

## 交互设计检查

- 主要动作触发前是否有必要输入；错误是否就近指出到具体字段？
- 提交后是否给“正在进行”的反馈，并防止重复提交造成副作用？
- 成功后下一步清楚吗；失败能重试且保留用户输入吗？
- 弹窗是否管理初始焦点、关闭后的焦点返回、Esc 行为和背景交互？
- 保存、删除、离开时，有没有破坏性操作确认与未保存变更提示？
- 长任务是否可取消/返回；加载动画是否掩盖了长期失败？

## 键盘与语义

优先使用原生 `button`、`a`、`label`、`input`、`select`、`table` 等语义元素。Tab 顺序应和视觉阅读顺序一致；不得用无语义 `div` 代替可操作控件却不补全操作语义。图标按钮须有可访问名称；输入要关联标签、错误描述和帮助文本。动态反馈宜用合适的状态消息，避免读屏器重复播报。

## 触摸与响应式

可点击区域应足够大，目标间隔合理；在 200% 缩放、窄屏及系统大字体下仍可访问关键控件。避免将拖拽设为唯一完成任务的方法；提供操作替代路径。必要时检查屏幕阅读器或自动化可访问性检查，工具缺失时注明未测试。

## 颜色、对比与动效

不要仅用红绿表达成功失败，搭配标签/图标/文字。为 `prefers-reduced-motion` 提供减少非必要动画的体验。可访问性检查不能被“组件库应该已经支持”替代；复用组件后仍须检查具体页面的组合方式。

## 优先级

**阻断操作、无法使用键盘、焦点丢失、重要信息看不到**优先修；其次是错误解释不清、反馈不足，最后才是纯视觉细节。
