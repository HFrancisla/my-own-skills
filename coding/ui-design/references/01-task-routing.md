# 01 · 任务分流：边界情况与风险尺度

`SKILL.md` 第 1 步是任务路径的**唯一入口**；此处处理容易误分的任务，帮助决定验证深度，而不是重复一套主流程。

## 易混淆的边界

- 用户说“优化页面”：先根据指定范围区分**修一个已知缺陷**还是**整体视觉方向重做**。只改按钮间距，就走局部修改；目标是重建整页视觉语言，才走整体改版。
- 用户说“像这张图”：优先还原**真实可比**的视口、内容比例、结构和字体；截图未出现的移动布局属于新适配，见 [04 布局与响应式](04-layout-responsive.md)。
- 用户说“比较三种风格”：先在灰度结构/内容组织层面分化方向；比较同一内容、状态和视口，不交付三种仅色相不同的皮肤。
- 用户说“评审”：保持只读，区分静态截图、源码与实际可操作页面的证据上限。即使发现 bug 也先汇报，不在评审路径私自改文件。
- 用户提供明确的设计规范：沿现有品牌/组件继续做，只有用户允许整体改版才调整基础语言；无必要时跳过三概念探索。
- 视觉需求同时包含 API/数据库：以用户明确授权的工程范围为界；必要联调可以做，但 UI Skill 不自动接管后端重构。

## 按风险调整验证深度

| 范围 | 要保留的最低证据 | 视情况增加 |
| --- | --- | --- |
| 局部属性/文案 | 受影响文件与实际结果；CSS 布局修改检查相邻区域 | 截图、局部键盘检查 |
| 一页新增/精修 | 宽窄视口、关键状态、主动作；精修前后对照 | 中间视口、复杂边界输入 |
| 多页或核心流程 | 关键任务端到端、共享组件周边回归、异常恢复 | 独立 UX 走查、跨设备/权限检查 |
| 设计体系级改动 | 明确 Token/组件源头、受影响页集合、迁移边界 | 团队确认和分批迁移计划 |

**回退条件：**缺乏真实任务依据，返回产品事实；灰度不通，返回结构；运行时缺关键状态，返回交互实现；真实截图有遮挡/溢出，修复后重验；缺工具或权限，把对应结论标成未验证。
