# 02 · 产品事实：先找用户任务，再找视觉风格

## 最小事实采集

从用户描述和当前代码提取：

1. **人**：主要使用者是谁？新手/专家？核心设备、语言和阅读场景？
2. **事**：进入页面前三秒希望看懂什么，主要动作和成功结果是什么？
3. **对象**：页面里的真正业务实体、字段、状态、关系、优先级。
4. **品牌**：Logo、现有设计 Token、措辞语气、用户已确认的方向。
5. **环境**：现有组件库、路由、持久化、权限、浏览器、断点、合规约束。
6. **交付**：设计说明、原型、单页代码、完整页面、截图评审中的哪一种？

不要先全盘读取代码仓库；只读有证据关联的文件、页面、配置。不能联网时不虚构竞品观察；可以在简报中标注“未核对外部参考”。

## 将参考拆成两层

| 参考类型 | 看什么 | 应输出什么 | 避免 |
| --- | --- | --- | --- |
| 视觉参考 | 构图密度、字重、层级、留白、色域、图像角色 | 可取的一至两条视觉原则 + 不适合本产品的部分 | 复制整页、无差别套风格 |
| 交互参考 | 入口→动作→反馈→恢复、空态、错误处理 | 操作步骤及其可观察反馈 | 只截默认态就认为完成研究 |

参考来源可包括用户提供的截图、公开产品、项目既有页面以及已有设计文档。外部产品可能随时间变化，无法验证时明确标注。

## 内容设计优先

- 标题写用户在做什么，不写空泛口号；按钮写动作而非“点击这里”。
- 表格字段体现业务判断，而非为填满列数制造字段。
- Mock 数据要合理，避免仿造真实客户评价、金额、增长数据或生产状态。
- 模拟和真实接入的区别放在交付说明里；若真实用户可能受误导，界面必须清楚标识。
- 状态名称来自实际业务：例如 `queued / running / failed / completed` 应与后端状态映射一致。

## 形成设计问题

尽量用「如何使 [角色] 在 [约束] 下完成 [任务]，同时降低 [障碍]」描述问题。

示例：`如何让运维人员在 1366px 宽度的工作台中，迅速定位异常 Agent 并查看失败原因，而无需记住状态颜色含义？`

输出到 `templates/design-brief.md`；仅记录真实已知事实和显式假设。
