# UI Design

目标是**可用、与产品相称且经证据验证的界面**。分别判断设计方向、实现正确性和真实使用效果；代码检查、截图观察、实际操作各有不同证明范围。

## 1. 路由：先决定做多深

根据用户交付目标与变更范围选择一条路径。边界不清时读取 [任务分流](references/01-task-routing.md)，不要只凭“优化”二字扩大修改范围。

| 路径 | 执行步骤 | 必须交付的证据 |
| --- | --- | --- |
| **局部修改**：用户已指定颜色、间距、文案或组件行为 | 核对约束 → 精确修改 → 检查受影响区域 | 变更位置、已执行检查与结果；按风险决定是否截图 |
| **新建/整体改版**：新页面、全新组件、显著视觉重构 | 下方 2–6 全流程；内部探索三个不同概念 | 方向取舍、关键状态、实际画面及操作验证范围 |
| **既有产品精修/交互调整** | 检查现有基线 → 定位问题 → 结构/状态设计 → 修改 → 回归 | 变更前后证据、主任务或状态回归 |
| **方案对比/截图还原** | 对比：先区分结构性方向；还原：先固定参考视口与内容 | 对比使用相同内容/视口；还原交付实际对照结果 |
| **只读评审** | 阅读目标 → 检查可获得证据 → 分级报告 | 每条问题有位置、观察、影响与建议；不修改代码 |

用户已确定风格、品牌、框架或组件库时，以这些约束为准。用户要求直接实现时继续实施；仅在缺失信息会改变核心方向且无法从现有项目推断时询问一个关键问题。阶段笔记和截图放在项目约定位置；没有约定时用 `.ui-design/<task-slug>/`，不写入 Skill 安装目录。

## 2. 获取事实：锁定任务而非风格词

仅查看相关需求、页面、组件、设计变量、项目规范和必要素材。按 [产品事实](references/02-product-context.md) 明确**用户、首要任务、业务对象、当前品牌、技术约束、目标设备、交付形态**。把用户提供的**视觉参考**与**交互参考**分别拆解。将未知内容标记为假设，真实数据、外部参考和已接入能力必须有来源。

**完成条件：**能写出一句可检查的任务目标、一个首要动作、已知硬约束及待验证假设；中大型任务可填 [设计简报](templates/design-brief.md)。只读评审到此进入第 5 步。

## 3. 定方向：让设计来自产品

新建/整体改版先按 [概念探索](references/13-concept-exploration.md) 从**核心对象、任务路径、视觉媒介**三个不同来源各提出一个简短候选；按品牌、设备、无障碍、素材和实现成本逐个淘汰。默认只对用户呈现所选方向；用户明确要求多方案时才按指定数量制作可比成品。局部修改及已有明确方向跳过探索。

用 [设计方向](references/03-design-direction.md) 确定一句**北极星**、每屏一个**视觉主角**和一个**主动作**。先验证灰度信息结构：对象、当前状态、行动入口、阅读顺序清楚；未通过则调整结构，再上颜色。按 [视觉辨识度](references/14-visual-distinctiveness.md) 提炼与产品事实相关的视觉语法和一个有意义的关键反馈；按 [视觉系统](references/05-visual-system.md) 映射既有 Token。多方案须至少在**骨架、字体/内容组织、主视觉、交互结构**中的两项有实质差异，而非仅换色。

**完成条件：**选定方向有产品依据和取舍理由，灰度下可找到主对象/主动作，关键失败风险可观察；新设计三个概念确有不同出发点。可用 [方向卡](templates/direction-card.md) 和 [视觉身份表](templates/visual-fingerprint.md) 留证。灰度不通过则留在本步，不用装饰弥补结构问题。

## 4. 实现：先打通一个真实任务

根据 [布局与响应式](references/04-layout-responsive.md) 设计宽窄视口行为；操作台读 [工作区规则](references/11-dashboard-workspaces.md)，展示型页面读 [落地页规则](references/12-landing-pages.md)。沿用项目技术栈、组件和约定，按 [工程实现](references/08-implementation.md) 先实现代表性页面或主要流程，再扩展。

对每个关键动作按 [交互与无障碍](references/06-interaction-accessibility.md) 核对 `触发 → 等待 → 成功/失败 → 恢复`，按实际需要覆盖焦点、空态、禁用和键盘操作。素材/动效确实服务任务时才读 [动效与素材](references/07-motion-assets.md)。模拟状态明确标识，不将演示数据说成真实服务。

**完成条件：**主任务有可观察的结果，失败可恢复；必要状态不缺席；响应式规则已落实到实现。纯方案任务则交付足以判断结构、状态与约束的设计材料，不把它宣称为可运行产品。

## 5. 验证：按证据能力得出结论

按 [视觉验收](references/09-visual-validation.md) 选择受影响视口、状态和路径：新页面至少宽屏/窄屏与核心任务，精修检查前后及相邻区域，小改动风险驱动。**实际打开并查看截图**才能判定视觉；**在可操作环境执行路径**才能判定交互。读取源码、构建成功或仅导出截图不能替代上述观察。

新页面、整体改版、重要品牌页：有隔离上下文且能看图的评审者时，按 [评审交接](references/10-review-handoff.md) 发起一轮独立视觉评审；复杂主流程可加独立 UX 走查。评审类型、问题标准和放行规则统一见 [专业评审](references/15-professional-review.md)。没有独立能力则做同量规自检并记录「未独立评审」，不要模拟独立审查。

**完成条件：**每项检查都记录实际结果、视口/状态与证据；P0 阻断已解决或明确标为不能交付，P1 修复或披露障碍；修复后重验受影响区域。没有取证能力的维度标**未验证**，而不是通过。

## 6. 交付：说清做了什么、证实了什么

参考 [交付模板](templates/delivery-report.md) 汇总方向及关键取舍、改动范围、核心动作/状态、测试/实图/走查的**通过、失败、未执行或受阻**、独立评审是否实际发生，以及假设和剩余风险。纯评审按 [只读评审模板](templates/design-review.md) 给可执行的 P0–P3 建议。

**完成条件：**交付的每个完成或通过声明能对应具体产物和证据；不包含不存在的截图、虚构的评分、假数据或未经授权的服务结果。

## 工具与成本边界

可选的 [`scripts/capture.mjs`](scripts/capture.mjs) 使用已有 Playwright 截图；[`scripts/make_comparison.py`](scripts/make_comparison.py) 生成离线方案对比页。两者均不自动安装依赖；按 `--help` 查看实际参数。依赖、网络、资产授权和权限应遵循项目/用户约束。无法运行浏览器时仍可完成可证明的源码级检查，并如实报告缺失的视觉/交互证据。禁止把截图、缓存、密钥和任务过程产物写入 Skill 包。
